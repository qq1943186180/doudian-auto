# 妙手任务记录、恢复与核验

这是 agent 应执行的流程约定，**当前没有专用程序、跨进程锁或自动状态校验器来强制执行**。不要声称“命令会拒绝重复发布”。使用现有项目记录机制；单一操作者串行运行，不把手工日志当可靠并发锁。

## 每款的证据

建议任务目录保存以下信息，文件名可随项目约定变化，内容不能缺关键语义：

| 记录 | 必需内容 |
|---|---|
| plan.json | 店铺和商品字符串ID、实际链接、目标字段及值、图片槽位与本地路径/哈希、非目标字段、版本、授权范围 |
| before-miaoshou.json | 独立新页读取的原商品、来源/时间、图片顺序、SKU与商业字段、审核状态及观察缺口 |
| before-doudian.json | 需要独立校验的原抖店版本与覆盖范围；与妙手有差异时先查清版本，不混成一个基线 |
| state.json | 阶段、提交状态、最后一步、时间、session、证据路径及未解决问题 |
| uploaded.json | 本地文件哈希→目标槽位→已观察到的远端资源对应、最终标题和预览字段 |
| submission.json | 保存前写入的意图、点击尝试时间、页面结果、实际任务ID及错误；未知保持 unknown |
| readback-*.json | 妙手和抖店各自读回内容、来源/时间、审核版本、目标比较及非目标差异、覆盖缺口 |

不要把请求头、Cookie、账户凭据或无关客户数据写入任务证据。商品素材与任务证据留在本地，不提交到代码仓库。

## 阶段与恢复

阶段用于区分外部事实，不是可以手改来绕过检查的开关。

| 阶段 | 表示什么 | 后续允许做什么 |
|---|---|---|
| prepared | 素材与计划准备好，未编辑 | 重新读取干净基线后编辑 |
| editing | 已开始填字段或上传，尚未确认最终预览 | 先查当前页及原任务；逐项核对已完成部分，再续原计划 |
| uploaded | 标题及素材在编辑窗口，尚未保存商品 | 比对计划与非目标字段后保存；页面丢失时重新判断，不能相信旧预览仍在 |
| submitting | 保存意图已落盘，点击可能已经发出 | 只读查保存/任务状态及抖店版本，不再次保存 |
| submitted | 有受理证据，最终内容尚待独立核验 | 只读核验，平台审核中则等待后复查 |
| verified | 抖店读回与目标、已覆盖的保留字段匹配 | 如实报告核验范围及消费者端审核状态 |
| rejected | 有明确校验失败或审核驳回证据 | 保留原因，修正须在授权范围内；只有确认上一尝试已结束且没有待处理提交才可新尝试 |

`submission_status` 与阶段分别记录 `not_attempted / unknown / accepted / failed`。不能把“保存窗口关了”“列表显示了新图”当受理成功。`unknown` 不是 `failed`。

### 编辑或上传中断

1. 恢复浏览器通道，找回同一 session/任务。先检查弹窗、当前商品、已有远端图和未保存输入，不刷新脏页。
2. 比较当前商品与原基线/目标。非目标字段改变或线上标题既不是原值也不是目标值，先调查其他操作者或托管任务，不覆盖。
3. 有明确“本地哈希—目标槽位—远端图片”对应且当前页匹配时跳过已完成项；来源不明的部分先查清，再按原计划处理。不能把“有5张图”当已经上传完。
4. 未进行保存且决定放弃时，记录原因和遗留编辑页；关闭/离页可能丢弃输入，应符合当前任务授权。不能释放或重建提交结果未知的任务来发起第二次保存。

### 保存中断或结果未知

- 网络异常后先查原任务是否存在待处理请求，再开独立只读页核对。当前 UI 若有历史记录或任务查询，使用当次观察到的入口，不编造轮询接口。
- 读到目标内容且保留字段匹配，可以记录“只读确认当前目标已满足”；缺少受理证据时不要补写“先前点击肯定成功”。
- 读到旧内容**不足以证明提交失败**，可能仍在排队/审核，也可能读的是旧生效版本。保留 unknown，稍后只读复查或请求必要的外部状态信息。
- 没有办法判断上一尝试是否结束时停止写入，报告具体未知点；不要自动重复点击、跨工具发布、清空日志或改 stage 强行继续。
- 只有取得明确失败/取消/任务结束证据，并确认没有仍在处理的提交，才能在原授权范围内记录新的尝试；保留前一次结果与原因。重试不是无条件自动循环。

## 两边独立核验

1. 保存前已有基线与编辑后预览。妙手保存后从新页重读相同商品；避免只读到保留在弹窗里的前端状态。
2. 通过实际页面的官方编辑入口取得 URL，核对域名 `fxg.jinritemai.com` 和同一商品 ID。`doudian-auto read` 是只读采集；不要把妙手任务目录传给抖店 `upload/submit/verify`，后者只认自己的任务契约。
3. 先核对读取版本：草稿、审核中版本、旧生效版本各自标注。两边不一致时不能选择更好看的版本宣布成功。
4. 按授权逐项比较：标题精确值；主图槽位与详情顺序；未改图片是否保留；SKU规格及标识、价格库存、类目品牌、运费发货、售后服务等实际采到的字段。
5. 图片上传可能重编码或更换 CDN；结合上传记录、远端内容和顺序核验，不要求本地字节哈希等于远端压缩图哈希。不能只比数量、去重URL后比较，或随意删除全部URL参数。
6. 未加载/虚拟SKU/缺失状态记 `not_verified`，不当成空值或相等；两边快照结构不同，先明确字段映射、单位及覆盖范围再比较，不能直接复用旧 `sections` 格式 compare 得出通过。
7. 抖店读回匹配可以记 verified；消费者端生效另看平台审核证据。价格库存等无授权变化，保留证据并停止新写入，不自动反向回滚。

## 连续5款实测与明确失败的处理

2026-10-26 按“仓库改5个上架”授权连续处理5款，每款改标题、方主图1/2和详情首图，其余图片保留。15张新图、32个SKU、价格库存及非目标商业字段逐款核验；5次保存受理、5次单品上架成功，官方新页逐款确认“上架”单选项选中。此为串行多款流程，不是一键批量上下架验收。

- 海绵首次保存有完整失败响应：`result=fail / recommendCategoryWaitAsync`，提示类目预测中稍后再试。保留失败响应和原编辑窗口，先处理其他款，待稍后重新核对预览再记录新尝试，第二次受理成功。不要把相同做法套到断连或提交未知。
- 杯架及拖鞋架第一次点击被本地必填属性拦住，DOM出现对应属性错误、完整捕获中没有保存请求。核对原始安装图后只补缺少项：杯架适配基面“橱柜层板”；拖鞋架安装“粘胶式”及基面“瓷砖墙面”。记录原空值、证据和新值，重新核验其余字段，再保存一次。不得为过校验猜规格、品牌、承重或更改类目；缺少可靠实物依据则保留缺口。
- 保存受理后立即读到旧标题且`draftStatus=2`，稍后新页才读到目标标题和`draftStatus=0`。保留两个版本，受理后只读等待，不重复保存。上架成功响应后列表按钮也可能短暂仍显示“上架”；只刷新查询并去官方核查，不再次点上架。
- 两张素材导入的`successUrls`仍是临时地址，保存后服务器才转为正式`png_m_...`。原上传/提交证据保持不变，下载最终读回素材，确认与对应本地文件SHA256和像素完全相同后另记资源映射；其余槽位逐个保持。不因URL变化重新上传或保存，也不把临时地址叫正式素材。
- 必填属性是本次明确、可追溯的新增项，比较时仅放行对应字段和精确新值；JSON属性文本先按结构比较，不因序列化顺序误判，也不豁免整个属性对象。官方控件新增会改变选择项数量，需对照实际DOM位置和全量妙手属性再核验。

已实测连续多款和上述明确失败后的修正；消费者端下单、保存断连及其他错误重试仍未验收，不主动制造线上失败。
